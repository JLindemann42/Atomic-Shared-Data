# Atomic shared data

The data both Atomic apps read, kept once. It is a git submodule at `shared/` in
[Atomic-Periodic-Table.Android](https://github.com/JLindemann42/Atomic-Periodic-Table.Android) and
[Atomic-Periodic-Table.Windows](https://github.com/JLindemann42/Atomic-Periodic-Table.Windows).
Before this, each app held its own copy and they had drifted: the Windows copy of the element files
carried 121 isotopes, 30 CAS numbers and NFPA ratings that Android never received.

| Folder | What | Read by |
|---|---|---|
| `elements/` | `elements_{lang}.json` for the twelve shipped languages | Android app assets and unit tests; Windows app content and `Atomic.Core.Tests` |
| `corpus/` | The Ask Atomic acceptance corpus, 39 TSV files | Android `CorpusTest`, Windows corpus tests, on every push. Both apps must pass every row. |
| `heldout/` | About a fifth of the corpus, frozen out of it by `tools/split_heldout.py` | The same tests with the held-out split selected, at release only |
| `datasets/` | `titles_{lang}.tsv`: every reference-table row's title in each of the eleven other languages, by canonical key. `explanations.tsv`: the written explanations for why-questions, with what each explains and the card it is shown with; `explanations_{lang}.tsv`: their text and trigger phrases in each language | Both apps' assets, for retrieval and answer headings (roadmap 1.3) and for why-questions (roadmap 2.4) |
| `language/` | `trigrams.tsv`, the language detector's character-trigram counts, generated by Android's `LanguageModelGoldenTest` from the app strings, stopwords, element descriptions and dataset titles | Both apps' assets, to decide which language a message is answered in (roadmap 1.4) |
| `golden/` | Tokenizer golden files, generated from the Kotlin tokenizer; `dataset_keys.tsv`, every reference-table row's canonical key, generated by Android's `DatasetKeyGoldenTest`; `fsrs.tsv`, the study coach's scheduler vectors, generated by `tools/fsrs_golden.py` | Windows `TokenizerGoldenTest`; both apps' `DatasetKeyGoldenTest` and `FsrsTest` |
| `sync/` | `study.md`: the study coach's cards, scheduler and `study` field in the progress document (roadmap 2.6) | Both apps' study coach and progress sync |

## Rules

- **Change data here, never in an app.** Edit, commit and push here, then bump the submodule in
  both apps in the same sitting, so neither ships data the other has not been tested against.
- **Held-out rows are not for tuning.** Do not look at `heldout/` while working on a change, do not
  move rows back, and never train on them. They exist to measure whether the corpus score
  generalises. Regression and reported-defect rows are never held out. New rows go to `corpus/`.
- **The corpus is the gate.** A change that adds behaviour adds rows that fail without it; no change
  may make a row that passed fail.
- **Line endings** follow `* text=auto`, as in both app repositories: LF in the repository, the
  platform's convention in the working copy. Scripts that rewrite the element files should keep the
  working copy's line endings, or every line shows as changed.
- **Not here:** the reference dataset tables (constants, equations, ions and so on). Those are
  Kotlin source in the Android app and the Windows tables are generated from them by
  `tools/port/kt2cs_model.py`, so they already have a single source; CI checks the generated files
  are current.

## Corpus format 2

A corpus file that declares `# corpus-format: 2` on a comment line before its header may use three
more columns. Both harnesses reject a column the declared format does not have, and a format they do
not know, so a misspelt column fails instead of being ignored.

| Column | Meaning |
|---|---|
| `expect_row` | The canonical key of the reference-table row the answer must come from, e.g. `geology/quartz`. Keys are `dataset/slug-of-title`, `#2` for a repeated title; see `golden/dataset_keys.tsv`. An explanation is `explanation/<key>`, from `datasets/explanations.tsv`. |
| `expect_value` | The number the answer must carry — a property's quantity, a row's value, an aggregate, the first element's value in a ranking (which pins a superlative's direction), the largest value of the first property compared, a molar mass, a mole count, the first element's value in a trend (which pins its field and its order), or the sum of a balanced equation's coefficients (9 for 4Fe + 3O2 → 2Fe2O3; an equation that did not balance carries none) — to within 0.1%. |
| `known_failure` | Why the row is expected to fail today. A failing known failure is reported but does not fail the build; one that passes fails it, so the mark comes off when the fix lands. |

Routing alone let wrong answers pass: "what is the mass of an electron" was answered from the
Pauli exclusion principle and still counted, because only the intent was checked.

## Data scripts

Scripts that rewrite the element files keep their formatting and line endings through
`tools/element_files.py`, so a change shows as the lines it changed. Each reports by default and
writes with `--write`, and running it twice changes nothing the second time.

| Script | What it does |
|---|---|
| `tools/split_heldout.py` | Freezes the held-out fifth of the corpus |
| `tools/normalize_isotope_names.py` | Writes every isotope name as Symbol-MassNumber (`Sb-103`), refusing any that disagrees with `iso_A` |
| `tools/translate_element_fields.py` | Translates `element_appearance` and `electrical_type` from `tools/translations/*.tsv` |
| `tools/stopword_candidates.py` | Proposes stopwords per language from the descriptions and the assistant's questions; the reviewed list is `STOPWORDS` in the Android app's `Lexicon.kt` |
| `tools/dataset_titles.py` | `--check` verifies every `datasets/titles_*.tsv`; `--new LANG` writes a template for a new language |
| `tools/fsrs_golden.py` | The study coach's FSRS-5 scheduler as a reference; `--write` regenerates `golden/fsrs.tsv`, and without it checks the file is current (roadmap 2.6) |
| `tools/element_descriptions.py` | Writes the element descriptions from `tools/translations/descriptions_*.tsv` and checks every description: no English clause, the symbol kept, no broken words; `--check` fails on any problem (roadmap 1.10) |

## Translated dataset titles

The reference tables are Kotlin source and stay English. Their row titles are translated here, one
file per language, with three columns: `key` from `golden/dataset_keys.tsv`, `title`, and
`reviewed`. A title may list other wordings after `|`: the first is shown, all are searched.
`dataset/<table>` rows, such as `dataset/poisson`, name a table itself. Keep numbers, Greek letters
and formulas as written (`α-Kvarts (SiO2)`); `--check` fails a row that drops one, a missing or
unknown key, and a `reviewed` value other than blank or `y`. The files are machine-translated, so
`reviewed` is blank until a native speaker has checked the row.

`tools/translations/*.tsv` have one English phrase per row and one column per language. To correct a
translation, edit its cell and re-run the script with `--write`. A phrase with no row is an error,
not an English fallback.

`tools/translations/descriptions_<lang>.tsv` are the exception: one element per row, with columns
`element`, `reviewed` and `description`, each a whole translation of the English description. They
cover the descriptions that were left part-English (roadmap 1.10), are machine-translated, and keep
`reviewed` blank until a native speaker has checked the row. Keep every number and the symbol as the
English has them; `tools/element_descriptions.py --check` fails a row that drops one. A description
changes what the language detector learns, so regenerate `language/trigrams.tsv` afterwards with
Android's `LanguageModelGoldenTest` and `-Pgolden.update=true`.

`golden/solubility.tsv` is generated by Android's `SolubilityGoldenTest`, like
`golden/dataset_keys.tsv` by `DatasetKeyGoldenTest`; Windows checks its solubility table against it.

## Updating an app to the latest data

```bash
git submodule update --remote shared
git add shared
git commit -m "Update shared data"
```

A fresh clone of either app needs `git clone --recurse-submodules`, or `git submodule update --init`
after cloning.
